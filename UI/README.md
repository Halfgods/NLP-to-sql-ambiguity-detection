# Clarion — Ambiguity-Aware NL → SQL (React UI)

A quiet, dark, gradient chat interface for the real project pipeline: the local
**Qwen2.5-Coder-1.5B-Instruct** detector decides whether a question is clear, asks for
a clarification when it is not, then Qwen may inspect the database with
read-only tools before generating one SQL query that is validated with SQLGlot
and executed against SQLite with read-only defaults and a confirmed write path.

## SQL model (Qwen2.5-Coder-1.5B, rebuilt fine-tune → GGUF)

The project has been re-based onto a dedicated SQL model, built locally:

| Artifact | Path |
| --- | --- |
| Teacher pairs (5,000) | `data/train_pairs.jsonl` (4.2k sql-create-context, 300 Gretel teacher pairs, 500 pairs over the real `students`/`courses` schema) |
| SQL + write QLoRA adapter (r=16, NF4) | `adapters/qwen25c-1.5b-sql-write-lora/` |
| Explicit INSERT/UPDATE training pairs | `data/write_pairs.jsonl`, generated by `scripts/build_write_pairs.py` |
| **Q4_K_M GGUF (~941 MB)** | `models/qwen25-coder-1.5b-sql-write-q4_k_m.gguf` — served by llama.cpp `llama-server` (CPU, mmap), port 18766 |
| Original read-only baseline | `models/backups/baseline-readonly-20261030/` (original GGUF and adapter; hashes verified) |
| Serving helper | `scripts/serve_sql.sh` |
| Accuracy harness | `scripts/eval_sql.py` — execution accuracy on `students.db` (30 hand-written gold pairs) + normalized-match on 40 held-out public pairs; reports to `evals/` |

The runtime lives in `model_runtime.py` (spawns/owns `llama-server`, one shared
canonical SQL system prompt) and `pipeline.py` (schema retrieval, read-only
validation, rollback-only write previews, and confirmed INSERT/UPDATE execution). Both the React worker and
the eval script share the same prompt, so chat behaviour and measured accuracy
match exactly.

## Run

Prerequisites (from the project root):

```bash
# fine-tune write support from the saved read-only SQL adapter
.venv/bin/python scripts/build_write_pairs.py
.venv/bin/python scripts/train_qlora.py --data data/write_pairs.jsonl \
  --resume-adapter adapters/qwen25c-1.5b-sql-lora \
  --out adapters/qwen25c-1.5b-sql-write-lora --epochs 8 --lr 1e-5
.venv/bin/python scripts/merge_lora.py \
  --adapter adapters/qwen25c-1.5b-sql-write-lora \
  --out models/merged-sql-write
scripts/build_write_gguf.sh

python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
```

Then:

```bash
cd UI
npm install
npm run dev        # http://localhost:5173
```

The Vite plugin starts `server/model_worker.py` with the project's
`.venv/bin/python`, keeps it alive, and loads Qwen **once**. The sidebar shows
the worker state (`loading` → `ready`); the first question waits for the load
instead of reloading the model per request. On first start, the demo tables
from `data/people.db` and `data/academics.db` are copied into
`UI/uploads/clarion.db`. Run `python scripts/build_demo_databases.py` to rebuild
the two source databases.

Set `CLARION_PYTHON=/path/to/python` if the interpreter is not in
`.venv/bin/python`. Set `CLARION_GGUF` to the backed-up original GGUF to roll
back the active model. Use **Node 22.13+** (the workspace uses `node:sqlite`).

`npm run build` produces a static bundle in `UI/dist/`; `npm run preview` serves
it with the same API middleware.

## What it does

- **Real ambiguity detection** — `ambiguity_detector.detect_ambiguity` asks
  Qwen (with the fine-tuned ambiguity adapter when present) for a decision and
  builds the interpretation options from the retrieved schema. The UI displays
  the decision, the fired rule (if any), and the model latency. It does not
  invent a confidence score.
- **Clarify before SQL** — ambiguous questions produce clickable interpretation
  chips. The selected option is sent back as the confirmed interpretation; SQL
  is generated only after that choice.
- **Read-only by default; confirmed writes** — ordinary questions run validated,
  row-capped `SELECT` queries. An explicit INSERT/UPDATE request must pass the
  deterministic intent gate, then the statement is previewed in a transaction
  that is rolled back. SQLite's authorizer permits only INSERT/UPDATE on the
  selected table. The UI shows the SQL and affected-row count and requires a
  separate confirmation before commit. DELETE and DDL are always rejected.
- **Named-metric guard** — if the question names a numeric column (for example
  *pending fees*), a query that uses a different numeric column is rejected
  even when it is valid SQL. The tool loop can repair it, the one-shot
  generator gets one grounded retry, and generation fails safe rather than
  answering a different question.
- **Read-only DB checks** — before the model writes SQL, it can call
  `list_tables`, `describe_table`, `sample_rows`, `distinct_values`, and a
  bounded `run_select`. The loop is capped, every call is shown under
  **DB checks** in the chat, and the same SQL validator protects the
  free-form query tool. If the loop cannot produce a valid query, the normal
  one-shot generator runs instead.
- **Uploads become real tables** — CSV/TSV/JSON files are imported into
  `UI/uploads/clarion.db`, a workspace seeded from the two demo databases. The
  Python pipeline retrieves that schema dynamically, so the model can query
  built-in tables and uploaded tables with the same validation path. SQLite
  database uploads import each ordinary table into the workspace under a
  file-prefixed name. Writes change the workspace copy, not the source file.
- **Inspectable** — every assistant turn carries the detector's decision/reason
  and the read-only tool trace; the SQL card shows exactly the statement that
  ran and the result table shows the returned rows (at most 100).

## Architecture

| Piece | Role |
| --- | --- |
| `server/api.js` | Vite middleware: `/api/upload`, `/api/datasets`, `/api/health`, `/api/query`, `/api/reset` |
| `server/model_bridge.js` | Spawns one long-lived Python worker; JSON-lines protocol, request queue, status |
| `server/model_worker.py` | Wraps `pipeline.analyze_question` / `pipeline.answer_question`; caches the detector result between the clarify and generate turns |
| `server/python.js` | Finds `.venv/bin/python` or honors `CLARION_PYTHON` |
| `server/workspace.js` | Seeds `UI/uploads/clarion.db` from `data/people.db` and `data/academics.db`, imports uploads as SQLite tables, reads live schema |
| `server/csv.js` | Dependency-free CSV/TSV parser + type inference |
| `../db_tools.py` / `../tool_agent.py` | Read-only DB inspection tools and the bounded `TOOL:`/`SQL:` loop |
| `src/App.jsx` | Conversation state, clarification round-trips, uploads, model-health polling |
| `src/components/` | `Chat`, `Composer`, `Sidebar`, `GradientBackdrop`, `icons` |

The demo data is split across `data/people.db` (`students`, `departments`)
and `data/academics.db` (`courses`, `enrollments`). `enrollments.student_id`
connects to `students.student_id`; join both tables in the workspace to combine
student and course data. Upload a CSV to query your own data alongside it.
