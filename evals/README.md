# evals/ — Clarion held-out evaluation suite

Everything in here is authored by the *brutal tester* role. It is independent of
the trained artifacts: when a peer's artifact is missing, `scripts/eval_full.py`
prints `NOT RUN (<reason>)` instead of pretending.

## Files

| path | what it is |
|---|---|
| `heldout/classifier_eval.jsonl` | 101 hand-labeled (schema, question) → {CLEAR, AMBIGUOUS, UNDERSPECIFIED} pairs across 6 schemas. Contract keys exactly: `schema_id`, `schema_text`, `question`, `label`. |
| `heldout/sql_eval.jsonl` | 30 gold SQL pairs for the students domain. Keys: `question`, `gold_sql`, `category`, `db`, `expected_result_row_count`. Every `gold_sql` was executed against its target DB at build time; the build aborts if anything fails to run clean. |

| `tmp/` | authoring + runtime helpers (documented below). Nothing here is part of the eval contract. |

Read-only DB access everywhere: `sqlite3.connect("file:<db>?mode=ro", uri=True)`.

## Label definitions (3-class, applied to ONE schema)

- **CLEAR** — the question has exactly one well-defined interpretation on this
  schema: one referent concept maps to a single column, the operation is
  determined by the phrasing, and no essential parameter (threshold, window,
  scope) is missing. A literal threshold given in the question ("above 90",
  "more than 4") is essential info that *is* present, so those are CLEAR.
- **AMBIGUOUS** — at least two plausible interpretations are supported by
  actual columns, and they are *materially* different: they require different
  SQL / different columns / different scope, and can return different answers
  (e.g. "best department overall" over average_marks vs attendance vs
  assignment_score). Ambiguity is judged **against the schema**, never rescued
  by a data coincidence (see Rule 5).
- **UNDERSPECIFIED** — needed information is missing:
  (a) the schema cannot answer the question at all (concept absent: hostel,
  age, phone, semester, survival data, falsity of positives …) — we map these
  here; a system still generating SQL for them is silently fabricating;
  (b) an essential policy parameter is unspecified by the user and cannot be
  derived from the schema (a pass cutoff, a "due" date rule, a maintenance
  threshold) — when the question has a *single* operational concept but no value
  for it;
  (c) the question needs data (dates, truth tables, ground truth, personal
  attributes) that no column or join can supply.

Priority when two things are wrong at once: an AMBIGUOUS column-fork outranks a
missing threshold; a missing *concept* (case a) outranks everything.

## Label-mapping rules (how borderline cases are resolved)

1. **Counting unit binds to the noun**: "how many patients…" ⇒
   `COUNT(DISTINCT patient_code)`; "how many screenings/visits" ⇒ row count.
   This is one reading, so such questions are CLEAR, not AMBIGUOUS.
2. **Missing threshold alone ⇒ UNDERSPECIFIED** ("cleared all assignments" with
   no pass mark). Missing threshold **plus** a supported ≥2-column fork ⇒
   AMBIGUOUS ("weak students", "struggling students": low marks vs low
   attendance is already a schema fork).
3. **Superlatives are one reading** when a single metric is named or
   linguistically forced ("who owes the most in pending fees" ⇒
   `pending_fees`, no other money-owed column exists ⇒ CLEAR). Superlatives
   without a metric ("best", "most overall", "used most") on a multi-metric
   schema ⇒ AMBIGUOUS.
4. **Exact literal value filters are CLEAR** ("visits in March", even though
   "this month"-style context questions would be UNDERSPECIFIED — required
   parameters that only the user's context can supply are missing info).
5. **No data rescue**: if interpretations coincide on the *current* data
   ("which department performs best" happens to be Electronics Engineering
   under marks, attendance and assignments on students.db today), the
   AMBIGUOUS label still stands — the ambiguity is between different queries,
   and tomorrow's rows can flip the answers. This was verified deliberately:
   `tmp/label_sanity_check.py` executes the candidate readings for every
   students-schema AMBIGUOUS pair and requires them to be materially different
   queries; the data-coincidence cases are documented, not exploited.
6. **"Schema cannot answer" ⇒ UNDERSPECIFIED** (rule a). These are kept in the
   eval so that a detector that funnels them into SQL generation gets punished
   by detection metrics, not excused.
7. Empty results do not change labels: "list students named X with zero matched
   rows" is still one well-defined interpretation (CLEAR) if every element of
   the question is schema-supported.

### The salary-variant pattern (explicit design requirement)

The same question text, "Who earns the most overall?", is CLEAR on
`employees_single_metric` (only `salary` can be meant) and AMBIGUOUS on
`employees_multi_metric` (base vs stock vs total-comp fork). This pair family
tests whether the classifier's AMBIGUOUS signal is driven by schema structure
rather than by question keywords. Same pattern round-trips through
"Compare pay between departments." vs "…by total travel reimbursement." (CLEAR).

### UNDERSPECIFIED pattern sets (explicit design requirement)

Three sub-families are present: (a) absent concepts at all (hostel, age,
backlogs, vaccination services, distance, insurance, women-screened, family
history, 5-year survival, false-positive ground truth, phone/owner contact,
"earned in March" time-slice, manager/leads, promotion, marital/gender
attributes), (b) missing single parameters (pass cutoffs, overdue / maintenance
rules, due-dates), (c) context-only parameters (excluded by design here because
the "this month" binding is unresolvable from schema alone — exact literal
filters appear in CLEAR instead).

### Near-miss pairs where naive keyword rules should fail (~12)

These were written so that a keyword/TODO-list detector scores badly (the pair
is labeled by schema semantics, not by surface):

1. "What percentage of students have cleared all assignments?" — UNDERSPECIFIED;
   keywords look like an easy CLEAR aggregate.
2. "Who are the top performers in internal marks?" — AMBIGUOUS; keyword `marks`
   invites a trivial map to `average_marks`, but "internal" makes it a fork.
3. "List the students who have pending fees." — CLEAR; keyword 'pending' invites
   a clarification for a threshold that isn't actually needed (presence test).
4. "Which department performs the best overall?" — AMBIGUOUS; keyword 'best'
   + superlative invites UNDERSPECIFIED, but it is a column fork.
5. "Who earns the most overall?" on `employees_single_metric` — CLEAR; the same
   keyword pattern is AMBIGUOUS on the multi-metric sibling (keyword rules
   cannot score both correctly).
6. "Which employees earned over 8000 in March?" — UNDERSPECIFIED; keyword shape
   screams the AMBIGUOUS salary fork; the real issue is no time column.
7. "List all vaccinations given in March." — UNDERSPECIFIED; month keyword maps
   fine, `vaccinations` does not.
8. "Which bike was used the most?" — AMBIGUOUS; 'most' keyword invites a simple
   superlative, but used-by-count vs used-by-minutes is a real fork.
9. "How many riders rode more than 25 km?" — UNDERSPECIFIED; numeric-filter
   keywords with no such column.
10. "How many women were screened?" — UNDERSPECIFIED; screening keywords hide a
    missing demographic column.
11. "How many pets weigh more than the average?" — CLEAR; comparative-to-average
    usually triggers "clarify threshold", but it is self-computable.
12. "Which results turned out to be false positives?" — UNDERSPECIFIED; looks
    like a value filter on `result`, actually requires ground truth that no
    column supplies.

unseen-schema behavior of both the classifier (T3) and any schema conditioning.

## SQL gold set (30 pairs)

- 24 pairs run against the **real** `students.db`;
- 6 JOIN pairs run against `evals/tmp/join_demo.db`, a deterministic 2+-table
  sandbox (students rows copied verbatim + `courses` + `enrollments`) created by
  `tmp/make_join_demo_db.py` (upsert-free: full recreate per run). The real
  students.db contains only the `students` table, so honest JOINs need this
  sandbox instead of feigning a JOIN target that does not exist.
- Categories: filter ×7, aggregate ×6, group_having ×6, order_limit ×5, join ×6.
- `expected_result_row_count` is recorded from an actual read-only execution of
  each gold (`tmp/build_sql_eval.py` re-verifies everything on rebuild).

## Authoring-time provenance (kept, documented, not eval contract)

  uniqueness/validity; writes the JSONL.

  per pair (the label quality artifact).
